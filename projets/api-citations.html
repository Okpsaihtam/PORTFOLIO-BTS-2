Avant-match

Contexte et problématique

Première mission de l'atelier de professionnalisation du BTS SIO : à partir d'un dépôt de départ fourni par l'équipe pédagogique, je devais construire le service qui stocke et distribue une collection de citations (texte, auteur, catégorie).

Dans une entreprise, ce type de service est la couche invisible qui alimente un site, une application mobile ou un outil interne. Il doit rester simple à consommer et ne jamais laisser passer une donnée incohérente.

Comment exposer des données de façon fiable, pour que n'importe quel client puisse les lire et les modifier sans jamais toucher directement à la base ?

Le plan de jeu

Objectifs

  • Comprendre et appliquer les principes de l'architecture REST
  • Implémenter les quatre opérations CRUD de bout en bout
  • Renvoyer le bon code HTTP à chaque situation
  • Valider et sécuriser toutes les données reçues
Mon poste

Missions principales

  • Modéliser la table citations et ses contraintes (texte 500 caractères, auteur 100 caractères)
  • Écrire le routeur et le contrôleur qui associent chaque verbe HTTP à une opération
  • Programmer l'accès aux données avec PDO et des requêtes préparées
  • Mettre en place la validation et un format d'erreur unique
  • Tester chaque route dans Postman, cas nominaux et cas d'erreur
  • Rédiger la documentation et publier une page de démonstration
Le déroulé

Étapes clés

  1. Analyse et modélisation

    Lecture du sujet, liste des besoins, puis schéma de la table : id, text, author, category, created_at, updated_at.

  2. Routage et contrôleur

    Un point d'entrée unique index.php lit la méthode et l'URL, puis appelle la bonne action du contrôleur.

  3. Accès aux données

    Requêtes préparées PDO sur SQLite, pagination (10 résultats par défaut) et filtre par auteur.

  4. Validation et erreurs

    Champs requis, longueurs maximales, réponses 400, 404 ou 500 au même format JSON avec le détail des erreurs.

  5. Tests

    Collection Postman couvrant les cinq routes, avec des scénarios volontairement invalides pour vérifier chaque code de retour.

  6. Documentation et démonstration

    Documentation des routes avec exemples cURL, JavaScript et Python, puis page de démonstration publiée sur GitHub Pages.

Numérique responsable

  • Réponses JSON légères et paginées : le client ne télécharge que ce qu'il affiche.
  • SQLite plutôt qu'un serveur de base de données : aucun service permanent à faire tourner pour un volume modeste.
  • PHP natif sans framework : moins de dépendances à maintenir et un code plus durable.

Bilan réflexif

Ce que j'ai appris

Une API se conçoit du point de vue de celui qui la consomme. Des codes HTTP cohérents et des messages d'erreur précis font gagner un temps considérable au développeur front.

Difficulté et solution

Mes premières réponses d'erreur avaient toutes un format différent. J'ai centralisé leur construction dans une seule fonction, ce qui a aussi simplifié les tests.

Pour aller plus loin

Ajouter des tests automatisés avec PHPUnit, une authentification réelle par jeton et une description OpenAPI générée automatiquement.

Ce projet a posé mes bases de développeur back-end : je sais désormais concevoir un service web qui protège ses données et reste simple à utiliser pour les autres développeurs.
